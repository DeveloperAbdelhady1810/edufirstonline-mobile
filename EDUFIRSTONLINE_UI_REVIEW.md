## Known gaps / flags (per your own "flag, don't invent" instruction)

- **No Live Sessions / Jitsi API exists on the backend** — unchanged from Step 4, still a separate future task.
- **The public course-detail endpoint doesn't expose whether the current student is enrolled.** Worked around by cross-checking the student's own `/my-courses` list client-side (an extra request) rather than inventing a new backend field — flagging in case a dedicated `enrolled: true/false` field would be worth adding server-side later.
- **Video/document/live lecture content and both purchase flows (course + package) render inside an in-app WebView** pointed at the existing web player/checkout via `POST /mobile/webview-ticket` — there's no native video player or native payment flow, by design (matches how the backend is actually built; not something this app should invent). Neither flow has a completion callback, so the app just refreshes its own state when the WebView screen is closed.
- **Lecture "mark complete" is a manual tap** (a checkbox next to each lecture, calling `POST /lectures/{id}/complete`), not automatic playback-position tracking — the `POST /lectures/{id}/progress` endpoint exists for real scrub-position tracking, but that requires a JS bridge into the WebView player that doesn't exist yet. Flagging as a possible Step 6 improvement, not built now.
- **No forgot-password endpoint exists** — the login screen's "نسيت كلمة المرور؟" link is a visual placeholder with no action, matching current backend capability.
- Login screen is now **wired to the real `POST /api/auth/login`** (previously a `TODO`) — the identifier field was narrowed from "phone or email" to "email" only, since the backend endpoint only validates/looks up by email.
- **Bug fix (real device testing found this)**: `setState(() => _future = someFuture)` was used in 9 screens for pull-to-refresh/retry. That's a real Dart footgun - an assignment expression evaluates to the assigned value, so the arrow closure actually returned the `Future` instead of `void`, and Flutter throws `setState() callback argument returned a Future` at runtime. Fixed by switching all 9 to a block-body closure (`setState(() { _future = x; })`).
- **Bug fix (real device testing found this)**: `MyCourse.fromJson`'s `progress` field crashed with a type-cast error because `/my-courses`' `progress` column is a raw SQL `coalesce(round(avg(...)), 0)` expression, which MySQL's driver returns as a numeric STRING, not a JSON number - confirmed live (`"progress":"0"` in the real response) rather than assumed. Added a shared `asInt`/`asNum` parser (`lib/utils/json_num.dart`) that accepts either shape, and applied it to every similarly-derived numeric field across the models as preventive insurance.
- **Bug fix**: free courses showed a price and routed through the paid Paymob/webview-ticket checkout instead of enrolling directly. The real backend's own web purchase route explicitly rejects that combination for a free course (`abort_if($course->is_free, 400, ...)`) and has a dedicated `enrollFree()` action instead - the mobile API had no equivalent at all. Added `POST /courses/{course}/enroll-free` mirroring that action exactly (same enrollment insert, points award, and student/teacher notifications), added `courses.is_free` to the `/courses` list select (it was missing there, only present on the detail endpoint), and updated the discover/detail screens to show "مجانًا" + a one-tap "اشترك مجانًا" button for free courses instead of a price and paid-checkout flow. Verified against production with a real temporary free course and a throwaway student (properly force-deleted afterward - the first cleanup attempt only soft-deleted the test course, which stayed visible in the live catalog since the public `/courses` endpoints query via `DB::table()` and don't respect `SoftDeletingScope`; caught and corrected within the same session).
- **Backend fix**: the mobile `POST /auth/register/student` endpoint only ever collected `name/email/password/phone/grade/education_stage/gender/age` — missing `division`, `study_mode`, `school`, `address`, and `parent_phone` entirely, and never created the linked parent account the real website registration does (`AuthController::registerStudent()` + `StudentRegistrationRequest`). Fixed by rewriting that route in `routes/api.php` to mirror the website's logic exactly (same validation rules, same conditional division requirement per stage/grade, same parent lookup-or-create, same `PointsService` award) — deployed and verified against production with two full round-trip registrations (division required/rejected correctly when missing, parent account created and linked correctly when present), then the throwaway test accounts were deleted. The register screen now collects all of these: parent phone, school, study mode (center/online), a division dropdown that only appears for grades that have one (exactly mirroring the web form's conditional behavior), and an optional address.

## 2026-09-14 — Push notifications actually reaching zero devices, root-caused and fixed

Reported as "notifications don't work." Two independent causes, both now fixed:

1. **`main.dart` skipped ALL push setup in debug builds** (`if (kDebugMode) return;`), added earlier specifically because `GoogleService-Info.plist` wasn't yet a bundled Xcode resource and `Firebase.initializeApp()` crashed the whole app before `runApp()` on iOS. That's fixed now (see above), so the blanket debug-mode skip was pure dead weight - and the reason `device_tokens` had **zero rows**: every normal `flutter run` test never even tried to register a token. Removed the gate; the try/catch around it is the real, permanent safety net and now runs in every build mode.
2. **The cron-driven queue worker was never actually configured on the server.** `App\Jobs\SendPushNotificationJob` (dispatched from `Notification::createFor()`) requires the one-line cron entry documented in `app/Console/Kernel.php`'s own comment - that's an hPanel-only step (Hostinger doesn't expose `crontab` over SSH), and it looks like it was never added for this domain specifically. Found 28 real `SendPushNotificationJob`s stuck in the `jobs` table, oldest ~11 hours old, zero attempts - genuine student activity (enrollments, new lectures) that correctly queued a push but nothing was ever running to send it. Manually drained the backlog (all completed instantly - no-op, since no tokens existed yet at that point). **You still need to add this cron entry in hPanel** (Advanced → Cron Jobs) for it to work going forward:
   ```
   * * * * * cd /home/u665632021/domains/edufirstonline.com/public_html && php artisan schedule:run >> /dev/null 2>&1
   ```
   This isn't push-specific - it's the same queue that also handles mail and anything else on the `default` connection, so this was silently affecting more than notifications.
3. **Smaller fix, matched to a reference implementation of this exact pattern from another project**: the FCM payload now sends `android.notification.channel_id: 'default_channel'` and an `apns.payload.aps` block (sound/badge), and `AndroidManifest.xml` now declares `default_channel` as the app's default notification channel via `com.google.firebase.messaging.default_notification_channel_id` - without it, a background/terminated-state push would still arrive but fall back to Android's generic channel behavior instead of this app's actual sound/importance settings.

## Google + Apple native sign-in

Native flow (not the web's redirect-based Socialite): the phone's Google/Apple SDK signs in on-device and hands the app a signed identity token; the app sends that token to the backend, which verifies it directly (Google via `tokeninfo`, Apple via `firebase/php-jwt` against Apple's JWKS) and finds-or-creates the account.

- **Backend**: `POST /auth/google` and `POST /auth/apple` (public) either log an existing user in (same `{token, user}` shape as `/auth/login`) or return `{needs_profile: true, ticket, name, email}` for a brand-new user — mirrors the existing `webview_ticket:` Cache-based ticket pattern, 15-minute TTL. `POST /auth/social/complete-profile` takes that ticket plus the same fields the web's social-complete form collects (name editable, phone, parent_phone, education_stage/grade/division, study_mode, school, gender, age — no role field, this app is student-only) and creates the Student + linked-parent rows exactly like `/auth/register/student` does.
- **Mobile**: `lib/services/social_auth_service.dart` wraps `google_sign_in` (pinned to `^6.3.0` deliberately — 7.x's Credential-Manager-based API needs its own separate native wiring this app doesn't need) and `sign_in_with_apple`. `LoginScreen` has "المتابعة عبر جوجل" (both platforms) and "المتابعة عبر آبل" (iOS only) buttons below the existing form. A new user is routed to `lib/screens/complete_social_profile_screen.dart` (same fields/pattern as `RegisterScreen`) before landing in `AppShell`.
- **Verified against production**: planted a disposable `social_register:` ticket via a bootstrapped PHP script, POSTed the full profile — got a real 201 with a working Sanctum token, and the created `users`/`students`/`parents` rows matched a normal registration's shape exactly (parent linked, `must_change_password` set). Force-deleted afterward. The `/auth/google` and `/auth/apple` audience/issuer rejection paths return clean 401 JSON (tested with garbage tokens) rather than 500s. `flutter analyze`/`flutter test`/`flutter build apk --debug` all clean.
